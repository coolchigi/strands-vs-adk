## Where we are

Earlier lessons established how to configure the AWS provider to point to LocalStack endpoints and declare foundational AWS network and storage resources. They also showed how explicit dependencies and resource references link objects like subnets and route tables to a VPC. With the infrastructure code written, the next stage of the workflow is previewing, executing, and tearing down those definitions.

## The idea

The core Terraform workflow consists of three consecutive stages: Write, Plan, and Apply ([source](https://developer.hashicorp.com/terraform/intro/core-workflow)). In the Write step, practitioners author infrastructure as code declarations ([source](https://developer.hashicorp.com/terraform/intro/core-workflow)). In the Plan step, changes are previewed prior to applying them ([source](https://developer.hashicorp.com/terraform/intro/core-workflow)). In the Apply step, reproducible infrastructure is provisioned ([source](https://developer.hashicorp.com/terraform/intro/core-workflow)).

Running speculative plans with `terraform plan` allows practitioners to preview upcoming changes, catch syntax errors, and verify that configuration behaves as intended ([source](https://developer.hashicorp.com/terraform/intro/core-workflow)). The `terraform plan` command reads configuration to determine desired state, queries provider APIs using state data to check the current state of resources, and describes necessary changes without modifying real-world infrastructure ([source](https://developer.hashicorp.com/terraform/cli/run)). While `terraform plan` does not apply modifications to real-world infrastructure, it can save the plan as a runnable artifact for `terraform apply` ([source](https://developer.hashicorp.com/terraform/cli/run)).

By default, running `terraform apply` performs a fresh plan and presents it to the user for confirmation before executing changes via provider APIs ([source](https://developer.hashicorp.com/terraform/cli/run)). The command displays this execution plan for confirmation prior to altering any infrastructure resources ([source](https://developer.hashicorp.com/terraform/intro/core-workflow)). When `terraform apply` asks for interactive confirmation, only the literal input `yes` is accepted to approve execution ([source](https://developer.hashicorp.com/terraform/intro/core-workflow)). Additionally, `terraform apply` can accept a pre-generated plan file generated by `terraform plan` instead of calculating a new plan ([source](https://developer.hashicorp.com/terraform/cli/run)).

The `terraform destroy` command asks the user for confirmation and destroys all resources managed by the current working directory and workspace using state data ([source](https://developer.hashicorp.com/terraform/cli/run)). A destroy operation behaves exactly like removing every declared resource from the configuration and running `terraform apply`, but avoids requiring any configuration file modifications ([source](https://developer.hashicorp.com/terraform/cli/run)).

## Worked example

Consider a workflow where we want to safely inspect, apply, and later clean up an S3 bucket defined in `main.tf`.

First, we generate and save a speculative plan without modifying anything:
```bash
terraform plan -out=tfplan
```
Terraform inspects local configuration and queries LocalStack for existing state data. It prints the execution plan showing `+ aws_s3_bucket.data will be created` and writes the binary execution artifact `tfplan`.

Second, we apply the exact pre-approved artifact:
```bash
terraform apply tfplan
```
Because a pre-computed plan file was supplied, Terraform executes the changes immediately via LocalStack provider APIs without asking for interactive confirmation, creating the bucket and updating the state file.

Finally, when we no longer need the local infrastructure, we initiate cleanup:
```bash
terraform destroy
```
Terraform reads the state file to identify the managed bucket, shows a plan indicating `- aws_s3_bucket.data will be destroyed`, and prompts for confirmation. We enter `yes`, and Terraform invokes the provider API to delete the bucket.
